# Account-bound rooms — v0.91.3

The supplied production policy report confirms unrestricted SELECT/INSERT/UPDATE
on all three multiplayer room tables and unrestricted writes to the legacy
nickname-keyed 3PT leaderboard. Profiles and match history already use user-ID
ownership rules. The report did not list API grants for the admin views; it does
not establish that emails were exposed.

## Installation order

1. Merge the companion v0.91.3 web-client pull request and wait for GitHub Pages to deploy.
2. In Supabase SQL Editor, run `supabase-room-security-v1.sql` in full.
3. Run `verify-room-security.sql` and return the result for review.
4. Reload two clients, create a NEW room and verify playing from phone to web.

The web client deliberately refuses insecure room access if the migration is
missing. Solo modes remain available. Old active rooms cannot be safely assigned
to accounts using names alone: their rows remain stored, but the players must
create new rooms. Profiles, wardrobe, saved scores and account credentials are
not deleted. The migration is transactional and was tested for repeat execution.

## Implemented protections

- A private membership registry assigns slots to authenticated Supabase user IDs,
  including anonymous-auth guests. Nicknames and room codes are not ownership.
- Replace all old room policies with member-only read/update and guarded creation.
- Atomic invitation joins lock the room, check the game kind and capacity, update
  the roster and assign membership in one transaction. Rejoining retains a slot.
- New account-scoped matchmaking RPCs reserve both players' slots and protect
  queue status/cancellation. The old SECURITY DEFINER queue RPCs are revoked.
- Bound room state size, immutable room identities, guest/creator limits and
  per-account join/matchmaking request limits.
- Revoke API access to admin views as defense in depth.
- Keep the old 3PT leaderboard readable but pause new writes: it has no user-ID
  ownership column. It needs a separate authenticated result design.

## Verification and limitations

`database-test.mjs` runs the actual SQL in PGlite (PostgreSQL), with production-like
tables, anon/authenticated roles and eight distinct test users. It verifies repeat
installation, private reads, third-party update rejection, blocked legacy room
adoption, revoked email-view access/legacy RPCs/score writes, every game kind,
six-player capacity, idempotent joins, five matchmaking modes, pending host
creation, queue ownership and failed-attempt rate limits. This is not a test
against the user's real Supabase project or its complete schema/triggers.

`online-test.mjs` exercises the real new browser join handlers and helpers;
`test.mjs`, `boot-test.mjs` and `dunk-regression.mjs` verify the hardened HTML and
existing game. Set `BU_TEST_HTML=/workspace/security-fix/index-online.html`.

Remaining: participants can still submit game state, XP and personal rankings.
Membership protects a match from unrelated accounts; it does not prove a legal
shot or prevent a participant from cheating. Competitive outcome/reward
validation, economy RPC auditing, authentication abuse controls and real-device
testing are still required before an unrestricted public/monetized launch.

Existing wardrobe/friends/progression RPC definitions have not been supplied or
audited. Their execute privileges and bodies remain a separate review item.

Build with `node build.mjs` then `node build-online.mjs`. The final file is
`index-online.html`, renamed to `index.html` when publishing. CSP hashes are
regenerated by the builder; do not hand-edit an inline script after building.
